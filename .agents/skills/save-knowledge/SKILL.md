# /digital-marketing-pro:save-knowledge

## Objectif

Enregistrer la connaissance de marque dans la couche de mémoire persistante (une base de données vectorielle que vous avez connectée — par exemple Pinecone via `@pinecone-database/mcp`) pour une récupération sémantique dans les sessions futures. Stocke les apprentissages de campagne, l'intelligence concurrentielle, les guidelines de marque, et les insights de performance avec un étiquetage de métadonnées approprié afin qu'aucune connaissance de valeur ne soit jamais perdue entre les sessions. Chaque élément stocké est haché pour la déduplication, tagué avec le contexte de marque, et indexé pour la recherche en langage naturel — transformant les apprentissages ponctuels en mémoire institutionnelle durable sur laquelle chaque agent peut s'appuyer. Conçu pour une capture de connaissance ciblée et intentionnelle — pour une synchronisation groupée entre sessions, utilisez plutôt `/digital-marketing-pro:sync-memory`.

## Entrées requises

L'utilisateur doit fournir (ou se voir demander) :

- **Contenu à stocker** : La connaissance à enregistrer — peut être du texte brut saisi directement, une référence à du contenu dans la conversation en cours (par ex. « enregistre l'analyse email qu'on vient de faire »), des données structurées issues d'un rapport ou audit de campagne, ou une URL vers une recherche externe. Le contenu est stocké tel quel avec une synthèse optionnelle pour l'entrée d'index
- **Type de contenu** : L'un des suivants : `guideline` (règles de marque, standards de voix, restrictions de style), `campaign-learning` (ce qui a fonctionné ou échoué dans une campagne avec les preuves à l'appui), `competitive-intel` (constats concurrentiels, positionnement, tarification, mouvements stratégiques), `performance-insight` (métriques, benchmarks, tendances, motifs statistiques), ou `brand-asset` (texte approuvé, modèles, références créatives, cadres de messages)
- **Tags** : Tags descriptifs pour une récupération filtrée — par ex. « email », « q4-2025 », « subject-lines », « audience-millennials », « paid-social », « black-friday ». Si non fournis, auto-suggérés en fonction de l'analyse du contenu utilisant le contexte de marque, la taxonomie sectorielle, et la détection de canal. Plusieurs tags encouragés pour une récupération plus riche
- **Contexte de source** : D'où provient cette connaissance — analyse de la session en cours, rapport importé, rétrospective de campagne, recherche externe, veille concurrentielle, ou apport d'équipe. Utilisé pour le suivi de provenance, la pondération de crédibilité lors de la récupération, et la conformité à la piste d'audit
- **Priorité (optionnel)** : `high` (faire remonter proactivement cette connaissance dans les contextes pertinents), `normal` (pondération de récupération standard), ou `low` (qualité archive, récupérer uniquement sur requête directe). Par défaut `normal`
- **Expiration (optionnel)** : Date après laquelle cette connaissance doit être signalée comme potentiellement obsolète — utile pour l'intelligence concurrentielle sensible au temps, les données de campagne saisonnières, ou les informations de tarification qui changent trimestriellement. Aucune valeur par défaut (la connaissance persiste indéfiniment sauf expiration)
- **Entrées liées (optionnel)** : Références à des connaissances déjà stockées auxquelles cette entrée se connecte — permet la liaison en graphe de connaissances et une récupération de références croisées plus riche

## Processus

1. **Charger le contexte de la marque** : Lire `~/.claude-marketing/brands/_active-brand.json` pour obtenir le slug actif, puis charger `~/.claude-marketing/brands/{slug}/profile.json`. Appliquer la voix de marque, les règles de conformité pour les marchés cibles (`skills/context-engine/compliance-rules.md`), et le contexte sectoriel. Vérifier également les guidelines à `~/.claude-marketing/brands/{slug}/guidelines/_manifest.json` — si présentes, charger les restrictions. Vérifier les SOP d'agence à `~/.claude-marketing/sops/`. Si aucune marque n'existe, demander : « Configurer d'abord une marque (/digital-marketing-pro:brand-setup) ? » — ou continuer avec les valeurs par défaut.
2. **Préparer le contenu pour le stockage** : Exécuter `memory-manager.py --action prepare-store` avec `content_type`, `tags`, et le contexte de source. Le script normalise le contenu, génère un hash de contenu SHA-256, structure la charge utile de métadonnées (brand_slug, content_type, tags, source, timestamp, priority, expiration), et valide que tous les champs requis sont présents. Si les tags n'ont pas été fournis, les auto-générer à partir de l'analyse du contenu.
3. **Vérifier les doublons** : Comparer le hash de contenu à l'index local à `~/.claude-marketing/brands/{slug}/memory/`. Si une correspondance existe, signaler le doublon — afficher les tags, la date et le résumé de l'entrée existante — et proposer de mettre à jour ses métadonnées (ajouter de nouveaux tags, rafraîchir l'horodatage, changer la priorité) plutôt que de créer un doublon. Si aucune correspondance, procéder au stockage.
4. **Vérifier les services de mémoire configurés** : Exécuter `python "${CLAUDE_PLUGIN_ROOT}/scripts/memory-manager.py" --brand {slug} --action get-memory-status`. Remarque : cela inspecte **uniquement les variables d'environnement** (par ex. si `PINECONE_API_KEY` est définie) — cela n'ouvre PAS de connexion en direct, et ne mesure PAS la capacité de stockage ni l'état de santé de l'index. Traitez sa sortie comme « quels backends sont configurés », et non « quels backends sont accessibles ». Si aucune variable d'environnement de base vectorielle n'est définie, stocker localement et recommander de connecter une base vectorielle pour un accès inter-sessions.
5. **Stocker via un MCP de base de données vectorielle (uniquement si un est connecté)** : DMP ne fournit pas de MCP de mémoire — rien n'est connecté par défaut. Si vous avez un serveur MCP de base vectorielle fonctionnel connecté (par ex. Pinecone), envoyez-lui la charge utile préparée pour l'embedding et le stockage avec toutes les métadonnées. Si vous avez également un serveur de mémoire inter-sessions fonctionnel connecté, synchronisez l'entrée là-bas ; si vous avez un serveur de graphe de connaissances fonctionnel connecté et que des entrées liées ont été spécifiées, créez des liens de relation. Si aucun n'est connecté, stocker localement. Voir `skills/context-engine/memory-architecture.md` pour le catalogue de couches et quels packages sont vérifiés-réels.
6. **Mettre à jour l'index local** : Exécuter `memory-manager.py --action log-stored` pour enregistrer la nouvelle entrée dans le registre local de hash de contenu avec l'ID de stockage, la référence de base vectorielle, l'horodatage, et la priorité. Mettre à jour l'état de synchronisation pour que les futures exécutions de `/digital-marketing-pro:sync-memory` ignorent cet élément comme déjà persisté.
7. **Confirmer le stockage** : Présenter la confirmation de stockage avec tous les détails — ce qui a été stocké, où cela a été stocké, les métadonnées appliquées, et des exemples de requêtes qui récupéreraient cette entrée.

## Résultat

Une confirmation de stockage structurée contenant :

- **Résumé du contenu** : Brève description de ce qui a été stocké, nombre de mots, hash de contenu pour référence de déduplication, et un résumé d'une ligne généré à partir du contenu pour l'affichage dans l'index
- **Type de contenu** : La classification appliquée — guideline, campaign-learning, competitive-intel, performance-insight, ou brand-asset — avec explication de pourquoi ce type a été sélectionné si détecté automatiquement
- **Tags appliqués** : Tous les tags attachés à l'entrée — tags fournis par l'utilisateur, tags auto-suggérés avec justification, et tags de contexte de marque (secteur, marché, slug de marque) ajoutés automatiquement pour l'isolation de namespace
- **Emplacement de stockage** : Quelle base de données vectorielle a été utilisée (Pinecone, Qdrant, ou local uniquement), nom du namespace ou de la collection, ID de stockage, et modèle d'embedding utilisé pour la vectorisation
- **Statut de déduplication** : S'il s'agit d'une nouvelle entrée ou d'une mise à jour d'une entrée existante — avec les détails sur les métadonnées fusionnées et la date de stockage de l'entrée d'origine
- **Priorité et expiration** : Le niveau de priorité défini (high, normal, low) et la date d'expiration si spécifiée, avec une note sur la manière dont ceux-ci affectent le classement de récupération futur
- **Entrées liées connectées** : Toute relation de graphe de connaissances créée avec des entrées existantes, avec confirmation de lien bidirectionnel
- **Total des éléments stockés** : Décompte courant du total d'éléments de connaissance dans **l'index de mémoire local** de la marque, ventilé par type de contenu (il s'agit du décompte local, pas d'un chiffre de capacité de base vectorielle en direct)
- **Indice de récupération** : Deux à trois exemples de requêtes de recherche qui feraient apparaître cette entrée — afin que l'utilisateur sache exactement comment la retrouver plus tard via `/digital-marketing-pro:search-knowledge`

## Agents utilisés

- **memory-manager** — Normalisation et synthèse du contenu, hachage SHA-256 pour la déduplication, détection de doublons par rapport à l'index local avec option de fusion des métadonnées, génération automatique de tags à partir de l'analyse du contenu, structuration des métadonnées avec validation des champs requis, préparation de la charge utile de base de données vectorielle et embedding, exécution du stockage via un MCP Pinecone ou Qdrant, création de relation de graphe de connaissances via Graphiti, mise à jour de l'index local et de l'état de synchronisation, et génération d'indices de récupération basée sur la sémantique du contenu stocké
