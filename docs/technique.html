02Structure du projet

Les routes sont organisées par façade — chaque groupe de routes correspond à un espace applicatif protégé par rôle.

# extrait — arborescence simplifiée
prisma/
  schema.prisma          # 24 modèles, migrations versionnées
  seed.ts                # compte admin cabinet + offres de démo
src/
  proxy.ts                # middleware — protège /client, /cabinet, /candidate
  app/
    (public-jobs)/         # job board public : /, /results, /jobs/[id], /trainings…
    (auth)/                # /login, /register, /register/cabinet, /api/auth/*
    client/                 # espace Client (protégé, rôle CLIENT)
    cabinet/                # espace Cabinet (protégé, rôle CABINET)
    candidate/              # espace Candidat (protégé, rôle CANDIDATE)
  components/
    ui/                   # Button, Card, Tag, Field, Tabs — primitives partagées
    mandats/ client/ cabinet/ candidate/ jobs/ training/ layout/
  lib/
    auth.ts                # config NextAuth complète (Node) — providers, callbacks
    auth.config.ts          # config partagée, compatible Edge (utilisée par proxy.ts)
    prisma.ts               # instance PrismaClient singleton
    rbac.ts                 # requireRole() / requireAdmin() / getSessionUser()
    storage.ts               # upload de fichiers (CV) — adaptateur disque local
    notify.ts                # écriture Notification + point d'extension e-mail
    validations/             # schémas Zod par domaine
  server/
    actions/                 # logique métier ("use server") par domaine
    services/
      mandatStateMachine.ts   # transitions de statut du mandat

03Modèle de données

24 modèles Prisma, organisés en six domaines. Le détail des relations et un schéma visuel sont dans le document Architecture.

Identité & comptes

User, Company, ClientProfile, CabinetProfile, CabinetInvite, Candidate

Mandats

Mandat, MandatStatusEvent, MandatMessage, MandateApplication

Entretiens

Interview, InterviewSlot

Job board

JobPosting, JobApplication, DirectMessage, JobSponsorship, JobAlert

Formations

TrainingCourse, TrainingSession, Enrollment

Transverse

Notification

Le rôle utilisateur (Role : CLIENT / CABINET / CANDIDATE) porte à lui seul l'aiguillage vers la bonne façade — aucun rôle Admin séparé : les droits d'administration cabinet sont un simple booléen isAdmin sur CabinetProfile.

04Authentification & autorisation

NextAuth est scindé en deux fichiers pour respecter la contrainte du middleware Next.js, qui s'exécute en Edge Runtime (aucun accès à Prisma/Node) :

  • lib/auth.config.ts — callbacks jwt/session uniquement, aucun accès base de données. Utilisé directement par proxy.ts.
  • lib/auth.ts — étend la config partagée avec les providers réels (Credentials, Google, LinkedIn conditionnels) et un callback signIn qui interroge Prisma pour créer/retrouver l'utilisateur.

Protection des routes

proxy.ts (middleware) redirige vers /login tout accès non authentifié à /client/*, /cabinet/* ou /candidate/*. Chaque layout de façade revérifie ensuite le rôle côté serveur via requireRole(), et chaque server action revérifie indépendamment rôle et propriété des données — la protection ne repose jamais sur un seul point de contrôle.

Connexion sociale

Google et LinkedIn sont ajoutés dynamiquement aux providers uniquement si leurs variables d'environnement sont définies (googleEnabled / linkedinEnabled, exportées pour l'UI). Réservée au rôle Candidat : le callback signIn crée le User + Candidate au premier passage, et refuse la connexion si l'e-mail correspond déjà à un compte non-candidat.

05Server actions & sécurité

Toute la logique métier vit dans src/server/actions/*.ts, sous forme de fonctions "use server" appelées directement depuis les composants client — pas de couche API REST intermédiaire. Chaque action suit le même schéma :

1. requireRole("CLIENT")           // rejette si non connecté / mauvais rôle
2. Validation Zod des données reçues
3. Vérification de propriété       // ex: mandat.companyId === user.companyId
4. Écriture Prisma (transaction si plusieurs tables)
5. revalidatePath() des pages concernées

Les transitions de statut de mandat passent systématiquement par mandatStateMachine.ts, qui valide la transition demandée contre une table de transitions autorisées et journalise chaque changement dans MandatStatusEvent — aucun code applicatif n'écrit Mandat.status directement.

08Vérification & tests

Aucune suite de tests automatisés n'a été mise en place ; la vérification a été faite en continu, à chaque fonctionnalité :

  • npm run build et npx tsc --noEmit systématiques avant chaque livraison.
  • npm run lint (ESLint, config Next.js) systématique.
  • Parcours de bout en bout dans un navigateur réel (Playwright headless) pour chaque fonctionnalité livrée : création de compte, dépôt de mandat, sourcing, entretiens, clôture, candidature, messagerie, sponsoring, alertes — avec vérification explicite des droits d'accès (un client ne peut pas voir le mandat d'un autre, etc.).

Recommandation

Ajouter une suite de tests automatisés (Vitest/Playwright) avant toute mise en production réelle — la couverture actuelle repose sur des vérifications manuelles répétées, pas sur des tests exécutables en continu.

09Déploiement

  1. Créer une base PostgreSQL managée (Neon ou Supabase, offre gratuite suffisante pour démarrer).
  2. Importer le dépôt GitHub dans un nouveau projet Vercel.
  3. Renseigner les variables d'environnement de la section 6 dans les réglages du projet Vercel.
  4. Vercel détecte automatiquement vercel-build et l'exécute — migrations puis build, en une étape.

Détail pas-à-pas (y compris l'obtention des identifiants Google/LinkedIn) dans README.md à la racine du dépôt.
